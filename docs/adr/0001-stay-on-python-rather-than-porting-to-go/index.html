    ADR 0001: Stay on Python and Rich rather than porting to Go⚓︎

    Date: 2026-08-05 Status: Accepted

    Problem⚓︎

    A partial Go port sits in local-code/tail-jsonl-go: a 282-line main.go stamped 1.3.0 that predates filters, time zone conversion, hidden keys, debug mode, and shell completions, plus a tests/ directory that is a copy of the Python suite rather than a Go one. Before spending more on it we needed three answers. How much faster would a finished Go port actually be, which features would be lost or become harder to maintain, and could a Go core exposed to Python through cgo and ctypes serve corallium and calcipy at the same time so that tail-jsonl could drop its Python dependencies and its PyPI release entirely.

    Measurements⚓︎

    Same 20,000-line corpus (8 MB, mixed simple and wide records, generated by benchmarks/throughput.py), output to /dev/null, macOS arm64.

    Variant 20k lines lines/sec per line
    tail-jsonl on Python 3.10 with Rich 6.00s 3,300 300 µs
    tail-jsonl-go as it stands, unbuffered fmt.Printf 0.79s 25,000 40 µs
    Buffered Go prototype written to find the ceiling 0.13s 154,000 6.5 µs
    Same prototype flushing per line, as a live tail needs 0.21s 95,000 10.5 µs

    Startup is 110ms per Python invocation against 3.5ms for a Go binary.

    The 154,000 figure is a ceiling rather than a forecast. The prototype skipped dotted paths, terminal-width wrapping, filters, zone conversion, and own-line keys. A faithful port would land somewhere around 30,000 to 80,000 lines per second, so roughly 10x to 25x.

    cProfile over print_record puts 69% of per-line time in rich_printer and Rich’s Text render and wrap path, 24% in the dotted library (get, remove, and parse on every key lookup), and json.loads low enough not to register. The speedup would come almost entirely from replacing Rich, which is also the part that would have to be rebuilt by hand.

    What a full port would cost⚓︎

    Ranked by how much maintenance each one adds:

    • corallium stops being one source of truth. rich_printer, Styles, get_level, and the Tokyo Night palette are shared with the other Python tools, so a Go port forks them and every palette or level change has to be made twice
    • dotted has no Go equivalent. It handles escaped dots, wildcards, and slices, and it backs --hide-key, --field-selector, dotted-key promotion, and empty-parent pruning. The existing port’s strings.Split(key, ".") walk is a different thing wearing the same name and would diverge on the cases in tests/data/test-dot-notation.toml
    • Python re becomes RE2, so lookaround and backreferences stop working in --include, --exclude, and --field-selector. RE2 gives linear-time matching in exchange, which removes catastrophic backtracking on user-supplied patterns
    • --time-format accepts any strftime pattern today, and Go’s reference-layout formatting is incompatible, so preserving the documented contract needs a shim such as lestrrat-go/strftime
    • Completions are generated by introspecting argparse actions in completions.py. Go would mean moving to kong or cobra, which supplies completions but changes flag semantics, including repeatable -e a -e b
    • Rich’s terminal handling covers width detection, word wrap, grapheme and east-asian width, NO_COLOR and FORCE_COLOR, and truecolor-to-256 degradation. Reachable with lipgloss, go-runewidth, and uniseg, plus a hand-rolled wrap
    • Go map iteration is randomized, so extra fields would print in a different order on every line unless decoding goes through json.Decoder.Token. The existing port has this bug
    • Unmarshalling into interface{} turns every integer into a float64, so numbers need json.Number. The existing port has this bug too
    • IANA zones need import _ "time/tzdata", about 450 KB, and ISO parsing becomes an explicit format list rather than fromisoformat leniency

    The RE2 and strftime breaks are acceptable, because the only user of those features is the maintainer. That removes two of the nine items above without changing the shape of the rest.

    The cgo variant, and why it fails⚓︎

    The proposal was to move the base of corallium (styles, level lookup, configuration loading) into Go, expose it to Python through cgo and ctypes, and let tail-jsonl-go and calcipy share one implementation. Possibly moving corallium from Rich to lipgloss along the way.

    Measuring the shared surface first is what settles it. corallium is 2,674 lines. The part tail-jsonl uses is styles.py (112 lines), rich_printer.py (84 lines), and the tomllib.py shim (12 lines). Most of that is data: five hex colors, six style names, and a ten-entry map of level names to numbers, with get_level and get_style as dict lookups.

    calcipy needs none of it. Its imports from corallium are LOGGER (9), file_helpers (8), vcs (3), file_search (3), tomllib (2), markup_table (2), code_tag_collector (2), shell, sync_dependencies, and can_skip. It imports styles and rich_printer zero times and uses rich directly zero times. Everything it does depend on is subprocess, pathlib, and pyproject parsing, which has no reason to leave Python and would be painful to return across an ABI.

    dotted is also not corallium’s. It is a third-party PyPI package that tail-jsonl depends on directly, so porting it is work with nothing upstream to share it with.

    The cost side is concrete. corallium ships today as one py3-none-any wheel. Adding buildmode=c-shared makes it platform-specific across macOS arm64 and x86_64, manylinux x86_64 and aarch64, musllinux, and Windows, which means six wheels, cibuildwheel, and CGO_ENABLED=1 with a C toolchain in CI. Any platform without a wheel falls back to an sdist that needs Go installed to build a dev-tooling library that is in the dev group of every project in the ecosystem. A c-shared library exposing exactly one lipgloss call measures 3.2 MB, 2.9 MB stripped, per platform. Rich is 2.3 MB of pure Python in one wheel that works everywhere.

    Replacing Rich with lipgloss inside corallium is not available at any price, because lipgloss is a Go library and every styled string would cross the boundary with a malloc and free per segment. corallium also depends on Rich for things an ABI cannot carry: Console width and tty detection, print_exception (which rich_printer calls on CRITICAL), and pretty_process.py, which is built on rich.progress with stateful, animated, multiprocessing-aware bars. Rich is not the bottleneck where corallium runs either, since calcipy tasks are one-shot dev commands whose 110ms of startup disappears into the subprocess they are about to spawn.

    Options considered⚓︎

    1. Full standalone Go rewrite, copying the roughly 120 lines of palette and layout logic into Go and dropping PyPI
    2. Go core with a cgo and ctypes boundary inside corallium, so Python and Go share one implementation
    3. Keep the PyPI entry point but ship a compiled Go binary as package data and os.execv it from scripts.py
    4. Stay on Python and spend the effort on the measured hot path instead

    Decision⚓︎

    Option 4.

    The tool is a stdin filter for a live pipe. At 3,300 lines per second it already outruns any log stream a human reads, so the only gain that would change daily use is startup latency, and 110ms does not justify a rewrite of roughly 900 lines of Python plus the corallium pieces. Option 2 fails on its own terms, since it would build a permanent six-platform binary-wheel matrix into the library that every Python project here installs, in order to share 200 lines that are mostly constants. Option 1 is coherent and stays available if the tool ever grows into file scanning or the web viewer idea, where Go’s concurrency would matter. Option 3 is the right mechanism if a Go implementation ever needs a Python entry point, because it needs no cgo, no ctypes, and no ABI.

    The performance work that remains is inside Python: caching parsed dotted patterns, and bypassing Rich’s wrap path for the common single-line record. Together those target the 93% of per-line time that the profile attributes to Rich and dotted.

    Consequences⚓︎

    • tail-jsonl keeps its PyPI release, its pipx and uv tool install path, and the calcipy toolchain
    • corallium stays a pure-Python wheel and keeps Rich, so the palette and level map have exactly one implementation and stay a single source of truth by construction
    • local-code/tail-jsonl-go is a dead end as written and should be treated as a spike rather than a branch to finish. Its randomized field order and float-widened integers are the two bugs to remember if it is ever revived
    • If a Go implementation is ever wanted, either for this tool or for the algorithmic parts of calcipy such as code_tag_collector and file_search, use a subprocess boundary rather than an ABI. A process boundary keeps static cross-compiled binaries, no CGO, no wheel matrix, and no ctypes memory discipline
    • Rewriting the --time-format and regex contracts against Go semantics is no longer on the table, so strftime patterns and Python re syntax stay documented as they are
    • benchmarks/throughput.py and the Go prototypes reproduce every number above. Rerun the benchmark before revisiting this decision, because the Python figure is the one that would have to move
